# 岗位画像设计

## 1. 文档目的

本文档用于统一岗位画像的数据定义、展示内容和生成规则，并作为后续岗位画像生成 Agent、数据库模型、接口 Schema 和前端页面设计的共同依据。

## 2. 岗位画像定义

岗位画像是基于一组描述同类岗位的真实招聘信息，提炼得到的结构化岗位说明。

岗位画像主要回答以下问题：

- 这个岗位主要负责什么工作？
- 从业者必须掌握哪些技能？
- 每项技能需要达到什么程度？
- 哪些能力属于加分项？
- 招聘市场通常有哪些学历、经验和证书要求？

岗位画像不是：

- 单条招聘信息的复制。
- 模型自由生成的职业百科。
- 招聘公司、福利和企业资质介绍。
- 没有招聘数据依据的职业推测。

## 3. 数据来源

岗位画像的主要数据来源为：

```text
平台采集的岗位信息
    或
用户上传的岗位信息
    ↓
岗位画像生成 Agent
    ↓
job_market_profiles
```

其中：

- 系统画像通常从 `job_raw_records` 获取招聘样本。
- 用户临时画像直接使用用户上传或输入的岗位信息。
- `job_market_profiles` 保存 Agent 最终提炼出的岗位画像。

平台只规定岗位画像的输出结构和字段约束，不预先规定画像字段的具体内容。岗位名称、岗位概述、岗位职责、技能要求等业务内容均由 Agent 根据输入材料生成。

第一版岗位画像流程暂不依赖 `job_directions`，也不要求画像必须关联平台预定义的岗位方向。

## 4. 画像类型

系统正式画像和用户临时画像使用同一张表，通过 `profile_type` 区分。

### 4.1 系统正式画像

由平台定期或人工触发生成，用于前端正式页面展示。

```text
profile_type = system
user_id = NULL
```

约束：

- 系统画像由平台采集的岗位信息生成。
- 重新生成策略由后续画像管理流程定义。
- 系统画像可以被所有用户查看。

### 4.2 用户临时画像

由用户通过平台 Agent 临时生成，用于满足个性化岗位分析需求。

```text
profile_type = temporary
user_id = 用户 ID
```

约束：

- 同一种岗位可以存在多份用户临时画像。
- 临时画像必须记录所属用户 ID。
- 用户身份和权限由 Java 层负责管理。
- Python 层只保存和使用 Java 层传入的 `user_id`。

## 5. 数据库字段

`job_market_profiles` 当前建议包含以下字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 岗位画像主键。 |
| `user_id` | VARCHAR(100) | 用户 ID；系统画像为空，临时画像记录所属用户。 |
| `profile_type` | VARCHAR(30) | 画像类型：`system` 或 `temporary`。 |
| `job_name` | VARCHAR(255) | 岗位画像名称。 |
| `job_overview` | TEXT | 岗位概述。 |
| `responsibilities` | JSONB | 岗位职责列表。 |
| `required_skills` | JSONB | 必备技能列表。 |
| `preferred_skills` | JSONB | 加分技能列表。 |
| `education_requirement` | TEXT | 学历要求总结。 |
| `experience_requirement` | TEXT | 工作经验要求总结。 |
| `certificate_requirement` | TEXT | 证书要求总结。 |
| `created_at` | TIMESTAMPTZ | 创建时间。 |
| `updated_at` | TIMESTAMPTZ | 更新时间。 |

岗位画像表不保存以下生成过程字段：

- 模型名称。
- 分析版本。
- 来源岗位 ID。
- 样本筛选条件。

如果后续需要生成任务追踪、审计或版本管理，应新增独立的岗位画像生成任务表。

## 6. 系统字段与 Agent 生成字段

岗位画像字段分为两类。

### 6.1 系统控制字段

以下字段由接口、编排流程或数据库控制，不由 Agent 决定：

- `id`
- `user_id`
- `profile_type`
- `created_at`
- `updated_at`

其中：

- `profile_type` 根据调用入口确定是 `system` 还是 `temporary`。
- `user_id` 由 Java 层传入；系统画像为空。

### 6.2 Agent 生成字段

以下岗位画像内容全部由 Agent 根据招聘信息或用户上传材料提炼：

- `job_name`
- `job_overview`
- `responsibilities`
- `required_skills`
- `preferred_skills`
- `education_requirement`
- `experience_requirement`
- `certificate_requirement`

平台负责定义这些字段的数据结构、枚举范围和校验规则，但不预设字段内容。

## 7. 岗位画像内容

### 7.1 岗位名称

`job_name` 由 Agent 根据全部输入材料提炼，应该表达这些招聘信息共同描述的岗位。

生成规则：

- 综合岗位标题、岗位职责和技能要求判断岗位名称。
- 合并相近或不同写法的岗位标题。
- 使用简洁、可理解的标准化名称。
- 不直接复制某一条招聘信息中的特殊岗位标题。
- 不添加输入材料无法支持的岗位类型或职责。

示例：

```text
AI应用开发
```

### 7.2 岗位概述

岗位概述使用一段简洁文本说明：

- 岗位的核心工作。
- 岗位的主要工作对象。
- 岗位通常需要交付的成果。

示例：

```text
负责将大语言模型、知识库和 Agent 能力集成到实际软件系统中，
完成智能问答、内容生成和业务自动化等 AI 应用的开发与优化。
```

岗位概述不再拆分为“岗位简介”和“岗位总结”两个重复字段。

### 7.3 岗位职责

`responsibilities` 使用 JSONB 列表保存。

每一项职责包含：

```json
{
  "name": "AI应用开发",
  "description": "基于大语言模型开发面向实际业务需求的智能应用"
}
```

完整示例：

```json
[
  {
    "name": "AI应用开发",
    "description": "基于大语言模型开发面向实际业务需求的智能应用"
  },
  {
    "name": "知识库建设",
    "description": "构建并维护基于 RAG 的企业知识库问答系统"
  },
  {
    "name": "Agent工作流开发",
    "description": "设计工具调用、状态流转和多轮执行流程"
  }
]
```

生成规则：

- 每项职责只表达一个明确工作任务。
- 合并含义相近的职责。
- 删除公司宣传、福利和岗位无关内容。
- 不生成招聘数据中没有依据的业务场景。

### 7.4 必备技能

`required_skills` 是岗位画像最核心的部分，使用 JSONB 列表保存。

每项必备技能包含：

```json
{
  "name": "Python",
  "category": "编程语言",
  "level": "熟练掌握",
  "requirement": "能够独立完成 AI 应用后端、接口和数据处理开发",
  "knowledge_points": [
    "异步编程",
    "异常处理",
    "类型标注"
  ],
  "tools": [
    "FastAPI"
  ]
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `name` | 技能名称。 |
| `category` | 技能分类。 |
| `level` | 需要达到的掌握程度。 |
| `requirement` | 对该技能的具体能力要求。 |
| `knowledge_points` | 需要掌握的知识点列表。 |
| `tools` | 与该技能相关的工具或框架。 |

掌握程度统一限定为：

```text
了解
熟悉
熟练掌握
能够独立应用
```

技能分类建议限定为：

```text
编程语言
计算机基础
后端开发
大模型应用
数据处理
数据库
工程化
部署运维
```

工具和框架属于技能内容，不单独形成岗位画像模块。

### 7.5 加分技能

`preferred_skills` 使用 JSONB 列表保存。

每项加分技能包含：

```json
{
  "name": "模型微调",
  "category": "大模型应用",
  "requirement": "了解 LoRA 等轻量微调方法并具备实践经验",
  "tools": [
    "Transformers",
    "PEFT"
  ]
}
```

生成规则：

- 仅提取招聘信息中明确属于优先条件或加分项的能力。
- 不强制生成掌握等级。
- 不把普遍必备技能错误归类为加分技能。

### 7.6 学历要求

第一版使用文本总结：

```text
多数岗位要求本科及以上，常见专业包括计算机科学、软件工程和人工智能，
部分岗位允许使用相关工作经验替代学历要求。
```

生成规则：

- 总结招聘样本中的主流要求。
- 允许说明专业要求。
- 不将少数样本的极端要求描述成普遍要求。

### 7.7 工作经验要求

第一版使用文本总结：

```text
多数岗位要求 1 至 3 年软件开发或大模型应用开发经验，
少量岗位接受具备相关实践能力的应届生。
```

生成规则：

- 总结常见工作年限范围。
- 说明是否普遍接受应届生。
- 可以描述相关领域经验，但不单独生成“项目经验要求”模块。

### 7.8 证书要求

第一版使用文本总结：

```text
招聘信息中通常没有普遍的强制证书要求。
```

生成规则：

- 只提取招聘信息中明确出现的证书要求。
- 没有明确证据时写“无普遍证书要求”。
- 不允许 Agent 自行推荐证书。

## 9. Agent 输入

岗位画像生成 Agent 的输入包括：

```text
平台岗位样本或用户上传的岗位信息
    ↓
岗位标题、招聘正文及其他有效字段
    ↓
岗位画像生成 Agent
```

系统正式画像的业务上下文由编排层提供：

```json
{
  "profile_type": "system",
  "user_id": null,
  "job_records": []
}
```

用户临时画像直接使用用户上传的岗位信息：

```json
{
  "profile_type": "temporary",
  "user_id": "10001",
  "uploaded_job_records": []
}
```

注意：

- `profile_type`、`user_id` 是编排上下文，不应要求模型生成。
- Agent 只负责生成岗位画像业务内容。
- 用户上传的岗位信息必须先转换成统一输入结构，再交给 Agent 分析。

## 10. Agent 处理流程

岗位画像生成 Agent 建议执行以下步骤：

1. 接收平台岗位样本或用户上传的岗位信息。
2. 清洗岗位标题和招聘正文。
3. 删除公司介绍、福利、企业资质等无关内容。
4. 综合全部材料提炼岗位名称。
5. 提炼岗位概述和岗位职责。
6. 提取技能要求和工具框架。
7. 区分必备技能和加分技能。
8. 合并同义技能和重复职责。
9. 根据招聘信息判断技能掌握程度。
10. 总结学历、经验和证书要求。
11. 按固定结构输出岗位画像内容。
12. 通过 Pydantic Schema 校验输出。
13. 由编排层补充 `profile_type`、`user_id` 等系统字段。
14. 将完整画像保存到 `job_market_profiles`。

## 11. Agent 输出边界

Agent 可以决定：

- 岗位名称。
- 岗位概述。
- 岗位职责内容和数量。
- 必备技能内容和数量。
- 加分技能内容和数量。
- 每项技能的分类、等级、知识点和工具。
- 学历、经验和证书要求的总结。

Agent 不可以决定：

- 画像属于哪个用户。
- 画像是系统画像还是临时画像。
- 数据库主键。
- 创建时间和更新时间。
- 是否覆盖已有系统画像。
- 数据访问权限。

## 12. 第一版明确不包含

第一版岗位画像暂不生成：

- 适合人群。
- 岗位难度。
- 独立的项目经验要求。
- 常见业务场景。
- 学习路线。
- 面试题。
- 职业发展路径。
- 薪资画像。
- 市场热度。
- 招聘样本数量。
- 来源岗位追踪信息。
- 模型名称和分析版本。
- 招聘数据中没有依据的推测。

## 13. 后续扩展

后续可以独立增加：

- 岗位画像生成任务表。
- 岗位画像历史版本表。
- 薪资和城市分布画像。
- 技能出现频率统计。
- 用户临时画像过期和清理机制。
- 岗位画像人工审核和发布流程。

以上扩展不应破坏当前岗位画像的核心展示结构。
