# 模型服务控制方案

## 1. 背景

当前 capability-backend 的 Agent 模型连接配置主要依赖 `model_gateway.yaml`。这种方式适合本地开发和早期验证，但不适合平台化管理。

平台后续不只是 Agent 会调用模型，知识库模块也会使用 embedding、rerank 等模型能力。因此模型配置应该作为平台级模型资源池，由数据库统一管理。

## 2. 设计目标

1. 使用一张 `model_configs` 表统一管理 chat、embedding、rerank 等模型。
2. 模型表只描述“这个模型怎么调用”和“它具备什么能力”。
3. Agent 模板必须显式绑定一个 chat 模型，不再依赖默认模型。
4. temperature、timeout、max_retries 等运行参数由 Agent 模板或本次调用控制，不放在模型配置表里。
5. embedding、rerank 第一版允许录入，但暂时不接入具体业务流程。
6. 前端可以管理模型配置，包括新增、查询、修改、删除、启用和禁用。
7. API Key 不明文返回给前端。
8. `model_gateway.yaml` 后续只作为本地开发兜底或初始化数据来源。

## 3. 核心字段语义

### 3.1 model_code

`model_code` 是平台内部唯一模型编码，也是前端可以直接展示的模型名称。

示例：

```text
chat-deepseek-pro
chat-qwen-plus
embedding-qwen-v3
rerank-gte-v2
```

### 3.2 model_name

`model_name` 是实际调用模型服务时传给模型接口的模型名。

示例：

```text
deepseek-chat
qwen-plus
text-embedding-v3
gte-rerank-v2
```

也就是说：

```text
model_code = 平台内部怎么叫它
model_name = 调模型接口时真正传什么
```

### 3.3 model_type

`model_type` 用来区分模型能力类型。

第一版支持：

```text
chat
embedding
rerank
```

### 3.4 is_multimodal

`is_multimodal` 用来标记模型是否具备多模态能力。

第一版先只存储，不接入具体逻辑。后续如果 Agent 支持图片、文件、视觉理解，可以用这个字段过滤可用模型。

## 4. 表结构设计

当前阶段只使用一张表：`model_configs`。

```sql
CREATE TABLE model_configs (
    id BIGSERIAL PRIMARY KEY,

    model_code VARCHAR(100) NOT NULL UNIQUE,
    model_name VARCHAR(255) NOT NULL,
    model_type VARCHAR(50) NOT NULL,

    base_url TEXT NOT NULL,
    api_key TEXT,
    api_type VARCHAR(50) NOT NULL DEFAULT 'openai_compatible',

    support_stream BOOLEAN NOT NULL DEFAULT FALSE,
    support_tool_calling BOOLEAN NOT NULL DEFAULT FALSE,
    support_structured_output BOOLEAN NOT NULL DEFAULT FALSE,
    is_multimodal BOOLEAN NOT NULL DEFAULT FALSE,

    enabled BOOLEAN NOT NULL DEFAULT TRUE,

    extra_config JSONB,
    description TEXT,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## 5. 字段说明

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 ID |
| `model_code` | 平台内部唯一模型编码，前端也直接展示这个字段 |
| `model_name` | 实际调用模型接口时传入的模型名 |
| `model_type` | 模型类型：`chat`、`embedding`、`rerank` |
| `base_url` | OpenAI 兼容接口地址或自建模型服务地址 |
| `api_key` | 模型服务密钥，后端使用，前端不明文返回 |
| `api_type` | 接口类型，当前默认 `openai_compatible` |
| `support_stream` | 是否支持流式输出 |
| `support_tool_calling` | 是否支持工具调用 |
| `support_structured_output` | 是否支持结构化输出 |
| `is_multimodal` | 是否为多模态模型，第一版先预留 |
| `enabled` | 是否启用 |
| `extra_config` | 扩展配置，例如额外 headers、特殊厂商参数 |
| `description` | 模型说明 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

## 6. 不放进模型表的字段

### 6.1 不需要 display_name

前端直接展示 `model_code` 即可。

如果模型编码设计得清楚，比如 `chat-deepseek-pro`，就没有必要再维护一套展示名称。

### 6.2 不需要 default_temperature

`temperature` 属于具体任务和 Agent 场景，不属于模型本身。

例如同一个 chat 模型：

- 岗位画像生成 Agent 可能需要 `temperature = 0.2`
- 主调度 Agent 可能需要 `temperature = 0.4`
- 创作类 Agent 可能需要 `temperature = 0.8`

所以 temperature 应该放在 Agent 模板的 `runtime_options` 中。

### 6.3 不需要 is_default

平台不设置默认模型。

每个 Agent 模板都必须显式配置自己的 `model_code`。如果没有配置，运行时直接报错，这样更清晰，也避免某个默认模型被误用。

## 7. Agent 模板绑定规则

Agent 模板通过 `runtime_options.model_code` 绑定模型。

示例：

```json
{
  "runtime_options": {
    "model_code": "chat-deepseek-pro",
    "temperature": 0.2,
    "timeout_seconds": 60,
    "max_retries": 2
  }
}
```

保存模板时需要校验：

1. `model_code` 必填。
2. `model_code` 在 `model_configs` 中存在。
3. 对 Agent 模板来说，绑定的模型必须是 `model_type = chat`。
4. 绑定的模型必须 `enabled = true`。

## 8. Agent 运行时解析流程

```text
AgentRunRequest
    ↓
读取 runtime_options.model_code
    ↓
如果 model_code 为空，直接报错
    ↓
查询 model_configs
    ↓
校验 model_type=chat、enabled=true、api_type=openai_compatible
    ↓
读取 base_url、api_key、model_name
    ↓
合并 Agent 模板或请求里的 temperature、timeout_seconds、max_retries
    ↓
创建 ChatOpenAI
    ↓
交给 create_agent 执行
```

## 9. API 设计

第一版接口建议放在 capability-backend：

```text
/agent/models/*
```

### 9.1 新增或更新模型

```text
POST /agent/models/upsert
```

请求示例：

```json
{
  "model_code": "chat-deepseek-pro",
  "model_name": "deepseek-chat",
  "model_type": "chat",
  "base_url": "https://api.deepseek.com",
  "api_key": "sk-xxx",
  "api_type": "openai_compatible",
  "support_stream": true,
  "support_tool_calling": true,
  "support_structured_output": true,
  "is_multimodal": false,
  "enabled": true,
  "extra_config": {},
  "description": "DeepSeek Chat 模型"
}
```

### 9.2 查询模型详情

```text
POST /agent/models/detail
```

请求：

```json
{
  "model_code": "chat-deepseek-pro"
}
```

### 9.3 查询模型列表

```text
POST /agent/models/search
```

请求：

```json
{
  "keyword": "deepseek",
  "model_type": "chat",
  "enabled": true,
  "page": 1,
  "page_size": 20
}
```

### 9.4 删除模型

```text
POST /agent/models/delete
```

请求：

```json
{
  "model_codes": ["chat-deepseek-pro"]
}
```

## 10. API Key 处理

第一版策略：

1. 数据库保存 `api_key` 明文。
2. 查询列表和详情时不返回真实 `api_key`。
3. 返回 `has_api_key` 表示是否配置了密钥。
4. 更新模型时，如果 `api_key` 为空，保留旧密钥。
5. 更新模型时，如果显式传入新 `api_key`，覆盖旧密钥。

后续可以增强为加密存储。

## 11. 前端调整

### 11.1 模型配置页

模型配置页从只读展示改为管理页：

- 模型列表
- 新增模型
- 编辑模型
- 删除模型
- 启用/禁用模型
- 按 `model_type` 筛选
- 显示是否已配置 API Key

### 11.2 Agent 模板编辑页

Agent 模板编辑页的模型选择改为：

1. 请求 `/agent/models/search`。
2. 只加载 `model_type = chat` 且 `enabled = true` 的模型。
3. 下拉展示 `model_code`。
4. 保存 `runtime_options.model_code`。

## 12. 第一版开发范围

第一版实现：

1. `model_configs` 数据模型。
2. 模型配置 CRUD API。
3. 查询接口隐藏 `api_key`。
4. Agent 模板支持并强制校验 `runtime_options.model_code`。
5. Agent 运行时根据 `model_code` 创建 ChatOpenAI。
6. 前端模型配置页改为可管理。
7. Agent 模板编辑页从模型表加载 chat 模型。

第一版暂不实现：

1. embedding 接入知识库。
2. rerank 接入检索流程。
3. 多模态模型调用逻辑。
4. API Key 加密存储。
5. 模型调用成本统计。
6. 模型健康检查定时任务。

## 13. 最终链路

```text
模型配置页
    ↓
写入 model_configs
    ↓
Agent 模板选择 chat 模型 model_code
    ↓
AgentRunRequest 携带 runtime_options.model_code
    ↓
AgentModelService 查询 model_configs
    ↓
创建 ChatOpenAI
    ↓
Agent 正常运行
```
