# 岗位技能评分检索优化方案

## 1. 文档定位

本文档记录 `job_skills` 查询能力的后续优化方案。

当前版本继续使用：

```text
normalized_name 精确匹配
    ↓
name / description 模糊匹配
    ↓
Agent 判断是否复用已有技能
```

后续技能数据量增加、写法变体增多后，可以升级为带相似度评分的候选召回。

本方案暂不立即修改现有接口和代码。

## 2. 优化目标

技能查询接口不负责直接判断两个技能是否相同，而是：

1. 根据查询词召回可能相关的技能。
2. 为每个候选技能计算字符串相似度评分。
3. 按评分从高到低返回候选列表。
4. 由 Agent 结合技能名称和描述判断是否为同一个技能。
5. Agent 确认没有相同技能后，才调用创建工具。

示例：

```text
查询词：Java

候选结果：
Java        score=1.00
Java Web    score=0.63
JavaScript  score=0.42
```

评分只表示字符串相似程度，不表示两个技能一定相同。

## 3. 核心职责

### 3.1 查询接口

查询接口负责：

- 标准化查询关键字。
- 精确匹配 `normalized_name`。
- 使用 PostgreSQL `pg_trgm` 召回相似名称。
- 使用名称和描述补充关键词召回。
- 计算并返回相似度评分。
- 按匹配优先级和评分排序。

查询接口不负责：

- 自动合并技能。
- 自动认定两个技能语义相同。
- 修改已有技能。

### 3.2 Agent

Agent 负责：

- 阅读候选技能的名称和描述。
- 判断候选技能是否与目标技能相同。
- 相同时直接引用已有 `skill_id`。
- 不同时决定是否继续查询或创建新技能。
- 创建前再次查询，降低并发重复创建概率。

### 3.3 normalized_name

`normalized_name` 继续保留，但职责收敛为：

- 识别空格、横线、下划线和点号等书写差异。
- 为完全相同的规范化名称提供精确匹配。
- 通过唯一索引防止明显重复。
- 在并发创建时提供数据库一致性兜底。

它不负责判断语义相似技能，例如：

```text
Java
Java Web
JavaScript
```

这些技能是否相同由 Agent 根据上下文判断。

## 4. 数据库能力

启用 PostgreSQL `pg_trgm`：

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

现有名称索引：

```sql
CREATE INDEX IF NOT EXISTS idx_job_skills_name_trgm
ON job_skills
USING GIN (name gin_trgm_ops);
```

继续保留标准化名称唯一索引：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_job_skills_normalized_name
ON job_skills(normalized_name);
```

如果后续需要对描述进行大规模相似查询，可以再评估是否为 `description` 添加索引。

## 5. 查询策略

推荐采用分层召回：

```text
第一层：normalized_name 精确匹配
第二层：name 的 pg_trgm 相似度匹配
第三层：name / description 的关键词匹配
```

精确匹配结果固定排在最前。

参考 SQL：

```sql
SELECT
    id,
    name,
    normalized_name,
    description,
    CASE
        WHEN normalized_name = :normalized_keyword THEN 1.0
        ELSE similarity(name, :keyword)
    END AS score
FROM job_skills
WHERE
    normalized_name = :normalized_keyword
    OR similarity(name, :keyword) >= :min_score
    OR name ILIKE '%' || :keyword || '%'
    OR description ILIKE '%' || :keyword || '%'
ORDER BY
    CASE
        WHEN normalized_name = :normalized_keyword THEN 0
        ELSE 1
    END,
    score DESC,
    length(name),
    name
LIMIT :limit;
```

初始参数建议：

```text
min_score = 0.2
limit = 10
```

阈值需要根据真实技能数据测试后调整，不能仅凭字符串评分自动认定技能相同。

## 6. 接口设计

接口路径保持不变：

```http
POST /job/skills/search
```

请求示例：

```json
{
  "keyword": "Java",
  "limit": 10,
  "min_score": 0.2
}
```

`min_score` 可以作为后续新增的可选参数，当前版本不需要立即加入。

响应示例：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "items": [
      {
        "id": 1,
        "name": "Java",
        "normalized_name": "java",
        "description": "通用面向对象编程语言",
        "score": 1.0,
        "match_type": "normalized_exact"
      },
      {
        "id": 2,
        "name": "Java Web",
        "normalized_name": "javaweb",
        "description": "基于 Java 的 Web 应用开发技术集合",
        "score": 0.63,
        "match_type": "name_similarity"
      },
      {
        "id": 3,
        "name": "JavaScript",
        "normalized_name": "javascript",
        "description": "主要用于 Web 开发的脚本语言",
        "score": 0.42,
        "match_type": "name_similarity"
      }
    ],
    "total": 3
  }
}
```

新增返回字段：

| 字段 | 说明 |
| --- | --- |
| `score` | 字符串召回评分，范围建议为 `0～1`。 |
| `match_type` | 匹配方式，例如精确标准化匹配或名称相似度匹配。 |

## 7. Agent 工具流程

`search_job_skills` 工具返回带评分候选后，Agent 应遵守：

```text
提取到目标技能
    ↓
调用 search_job_skills
    ↓
检查候选名称、描述和 score
    ↓
存在语义相同技能
    → 直接引用已有 skill_id
    ↓
不存在语义相同技能
    → 必要时补充资料
    → 再次调用 search_job_skills
    → 调用 create_job_skills
```

Agent 不应只根据 `score` 判断：

```text
score 高 ≠ 一定是同一技能
score 低 ≠ 一定不是同一技能
```

例如：

- `Java` 和 `JavaScript` 字符串相似，但不是同一技能。
- `PostgreSQL` 和 `Postgres` 字符串不完全相同，但通常指向同一技能。

## 8. 暂不使用 Embedding

第一阶段不使用 Embedding，原因：

- 技能名称短，字符串精确和相似度查询更可解释。
- `Java` 与 `JavaScript` 等名称容易产生语义误判。
- 当前技能数据规模较小。
- Agent 已经可以根据候选描述完成语义判断。
- Embedding 会引入向量生成、更新和索引维护成本。

满足以下情况后再考虑混合检索：

- 技能数量达到数千或更多。
- 同义名称大量增加。
- 字符串召回经常漏掉语义相同技能。
- 已经具备稳定的技能 Wiki 或较完整描述。

未来可采用：

```text
normalized_name 精确匹配
    ↓
pg_trgm 字符串召回
    ↓
Embedding 语义召回兜底
    ↓
Agent 最终判断
```

## 9. 验收标准

实施本优化时至少满足：

1. 查询 `fast-api` 时，`FastAPI` 排在第一位且 `score=1.0`。
2. 查询 `Java` 时，可以返回 `Java`、`Java Web` 和 `JavaScript` 等候选。
3. 精确标准化匹配始终优先于模糊匹配。
4. 候选结果包含 `score` 和 `match_type`。
5. 查询接口不自动合并或修改技能。
6. `create_job_skills` 继续依赖 `normalized_name` 唯一索引防止明显重复。
7. Agent 模板明确要求创建前先查询，并由 Agent 判断候选语义。

## 10. 实施时机

建议在以下任一情况出现时实施：

- `job_skills` 数据量明显增长。
- Agent 经常因为名称写法不同重复创建技能。
- 关键词查询无法稳定召回候选技能。
- 开始建设技能 Wiki 和技能关系网络。

在此之前，当前“标准化精确匹配 + 关键词模糊匹配”的实现足够支撑第一版。
