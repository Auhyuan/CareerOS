# 历史节点创建分支

## 目标

用户可以从任意已经保存稳定阶段结果的历史节点继续修改，形成一条新的方案演进路线。原分支及其节点保持不变，新分支拥有独立的 Agent 会话和 Checkpoint。

## 接口

```http
POST /workflow/branches/create
Authorization: Bearer <access_token>
Content-Type: application/json
```

```json
{
  "source_node_id": "历史节点 UUID",
  "branch_name": "需求确认方案 B",
  "expected_result_version": 2
}
```

`expected_result_version` 是来源节点结果的乐观锁版本。若用户看到节点后，节点结果又被更新，接口会拒绝基于旧内容创建分支。

## 创建规则

1. 来源节点必须属于当前登录用户。
2. 来源节点状态必须为 `ready` 或 `completed`，并且已经保存非空阶段结果。
3. 新分支记录 `source_branch_id` 和 `source_node_id`，用于恢复树状来源关系。
4. 新节点与来源节点处于相同阶段，`parent_node_id` 指向来源节点。
5. 新节点复制 `input_context`、`result_data` 和 `summary`，作为继续修改的业务基线。
6. 新节点状态重置为 `working`，`result_version` 重置为 `0`，`handoff_context` 清空。
7. 新节点生成全新的 `agent_thread_id`，不复制 `checkpoint_id`，因此不会继承旧分支的 Agent 运行状态。
8. 项目的 `current_branch_id`、`current_node_id` 和 `current_stage` 切换到新分支节点。
9. 原分支、原节点和原 Checkpoint 不做任何修改。

## 树状关系

```text
项目准备
  ↓
需求确认 A
  ├── 策划方向 A
  └── 需求确认 B（新分支、新 agent_thread_id）
        ↓
      策划方向 B
```

新分支首节点的 `sequence_no` 沿用来源节点序号。序号只要求在同一分支内唯一，因此既能保持阶段顺序，也不会与原分支冲突。

## 后续调用

创建成功后，前端使用响应中的新 `node.node_id` 调用：

```http
POST /workflow/nodes/messages
```

Agent 会收到复制后的 `current_stage_result`，用户可以直接说明需要修改的内容。Agent 完成修改后通过 `save_stage_result` 保存新版本，随后仍使用 `/workflow/nodes/advance` 进入下一阶段。
