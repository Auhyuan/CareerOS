# Hai-agent 多阶段分支工作流与节点结果交接方案

## 1. 方案目标

Hai-agent 将活动策划拆分为项目准备、需求确认、策划方向、方案生成和反馈修改等阶段。每个阶段由独立 Agent 节点完成，并通过标准化结果向下一个节点交接。

本方案确定以下原则：

1. 一个步骤节点对应一个阶段 Agent 和一套独立 Checkpoint。
2. 节点内部中断恢复复用当前 Checkpoint，跨节点不复用也不复制 Checkpoint。
3. 所有阶段统一使用 `save_stage_result` 保存 JSON 结果。
4. Agent 只能保存结果，不能自行推进阶段或创建分支。
5. 保存结果并校验通过后，用户才能点击进入下一步。
6. 从历史节点继续时创建新分支，原分支保持不变。

## 2. 核心模型

- **分支**：项目从某个历史节点开始延伸的一条方案演进路径。
- **步骤节点**：一次独立的阶段执行，例如需求确认或方案生成。
- **Checkpoint**：只保存一个步骤节点内部的 LangGraph 运行状态、中断点和工具消息。
- **阶段结果**：Agent 在当前节点整理出的业务 JSON。
- **交接上下文**：当前节点完成后传给下一节点的累计业务数据。

```text
上一个节点完成
    ↓
冻结节点结果
    ↓
生成 handoff_context
    ↓
创建下一个节点
    ↓
创建新的 thread_id / Checkpoint
    ↓
加载下一阶段 Agent 模板
    ↓
将 handoff_context 作为节点输入
```

## 3. 用户、项目与节点隔离

系统使用四级标识组织数据：

```text
user_id
  └─ project_id
       └─ branch_id
            └─ node_id
```

1. `user_id` 隔离不同用户，保存在项目表中。
2. `project_id` 隔离同一用户的不同活动策划项目。
3. `branch_id` 标识项目中的一条方案演进路线。
4. `node_id` 标识分支中的一个独立阶段执行节点。
5. 子表不重复保存 `user_id`，通过 `project_id` 归属项目；访问业务数据时必须先使用 `user_id + project_id` 校验项目归属。
6. 项目保存 `current_branch_id` 和 `current_node_id`，用于恢复用户当前工作位置。

### 3.1 节点关系

节点只保存 `parent_node_id`，不保存 `next_node_id`。

- `parent_node_id = null`：根节点。
- 查询 `parent_node_id = 当前 node_id`：获取当前节点的所有直接子节点。
- 没有子节点：当前节点是叶子节点。
- 一个子节点：线性推进。
- 多个子节点：从当前节点产生了多个后续分支。

不同时保存父节点和下节点，可以避免双向关系更新不一致。

### 3.2 节点序号

`sequence_no` 是分支内展示序号，只负责排序，不作为父子关系依据。

```sql
UNIQUE (branch_id, sequence_no)
```

前端展示单条分支时按 `sequence_no ASC` 排序；展示完整流程树时使用 `parent_node_id` 构建父子关系。

## 4. Checkpoint 隔离

Checkpoint 的隔离单位是步骤节点，不是项目或整条分支。

```text
一个步骤节点 = 一个独立 thread_id = 一套独立 Checkpoint
```

节点尚未完成时，用户补充信息、确认表单或中断恢复继续使用同一个 `thread_id`。进入下一节点时创建新的 `thread_id`，不得复制旧 Checkpoint 或完整消息历史。

Checkpoint 只负责节点内部运行恢复和排查。阶段结果、方案版本和历史树由 Hai-agent 业务数据库保存。

## 5. 通用结果保存工具

所有阶段统一使用：

```text
save_stage_result
```

### 4.1 模型传入参数

```json
{
  "result": {
    "project_name": "新品发布会",
    "activity_goal": "提升新品曝光",
    "target_audience": ["行业客户", "媒体"],
    "budget": null,
    "missing_items": ["活动预算", "活动时间"]
  },
  "result_summary": "已完成项目资料整理，仍缺少预算和活动时间"
}
```

### 4.2 Runtime Context 注入参数

以下字段由系统自动注入，模型不填写：

- `project_id`
- `branch_id`
- `node_id`
- `stage_code`
- `agent_id`
- `run_id`

工具只能更新 Runtime Context 指定的当前节点，避免模型写错项目、分支或节点。

### 4.3 工具职责

`save_stage_result` 负责：

1. 校验当前节点是否允许更新。
2. 根据 `stage_code` 加载阶段输出规则。
3. 校验并保存 `result`。
4. 更新结果摘要和结果版本号。
5. 根据校验结果将节点保持为 `working` 或更新为 `ready`。
6. 返回 `can_advance`。

工具不得创建下一节点、切换阶段、创建分支或直接把节点标记为 `completed`。

推荐返回：

```json
{
  "saved": true,
  "node_id": "node_xxx",
  "result_version": 3,
  "node_status": "ready",
  "can_advance": true
}
```

## 6. 阶段结果约束

所有节点都使用 JSONB 保存结果，但每个阶段应配置自己的 `output_schema`，不能让 JSON 完全无约束。

```json
{
  "stage_code": "project_preparation",
  "output_schema": {
    "required": [
      "project_summary",
      "confirmed_information",
      "missing_information"
    ]
  }
}
```

| 阶段 | 主要输出 |
|---|---|
| 项目准备 | `project_summary`、`materials`、`confirmed_information`、`missing_information` |
| 需求确认 | `confirmed_requirements`、`constraints`、`unresolved_items` |
| 策划方向 | `creative_directions`、`selected_direction`、`selection_reason` |
| 方案生成 | `proposal_version_id`、`proposal_summary`、`evidence_refs` |
| 反馈修改 | `feedback_summary`、`proposal_version_id`、`change_summary` |

这样仍然只需要一个保存工具，同时可以保证不同阶段的输出稳定可用。

## 7. 节点状态

| 状态 | 说明 |
|---|---|
| `working` | Agent 正在处理，结果尚未满足进入下一步的条件 |
| `ready` | 已保存合法结果，允许用户进入下一步 |
| `completed` | 用户已确认进入下一步，当前节点结果已经冻结 |
| `failed` | 节点执行失败 |
| `cancelled` | 节点已取消 |

```text
working --保存合法结果--> ready --用户进入下一步--> completed
    └--执行失败-------> failed
ready --再次更新结果--> ready 或 working
```

Agent 不直接控制 `completed` 状态。

## 8. 进入下一节点

建议提供接口：

```http
POST /workflow/nodes/{node_id}/advance
```

用户点击“进入下一步”后，后端在一个事务中：

1. 锁定当前节点。
2. 校验项目、分支和节点归属。
3. 校验节点状态为 `ready`。
4. 校验提交的 `result_version` 仍是最新版本。
5. 将当前节点标记为 `completed` 并冻结结果。
6. 构建当前节点的 `handoff_context`。
7. 创建下一步骤节点，初始状态为 `working`。
8. 为新节点创建新的 `agent_thread_id`。
9. 将 `handoff_context` 写入新节点的 `input_context`。
10. 更新分支的 `head_node_id` 并返回下一节点。

前端可根据 `can_advance=true` 点亮按钮，但后端必须再次执行完整校验，不能只依赖前端状态。

## 9. Handoff Context

推荐统一格式：

```json
{
  "project_id": "project_xxx",
  "source_node_id": "node_xxx",
  "completed_stage": "requirement_confirmation",
  "project_facts": {},
  "confirmed_requirements": {},
  "selected_direction": null,
  "proposal_version_id": null,
  "assumptions": [],
  "unresolved_items": [],
  "evidence_refs": [],
  "result_summary": "客户需求已经确认"
}
```

交接上下文应保存下游需要的累计业务事实。大型正文只保存业务对象 ID 和摘要，附件保存 `file_id`，知识库保存 `knowledge_id` 和证据引用。不得包含完整思考过程、无关工具消息或全部历史对话。

## 10. 创建新分支

```text
选择已完成历史节点
    ↓
读取节点冻结的 handoff_context
    ↓
创建 workflow_branch
    ↓
创建新分支首个步骤节点
    ↓
创建新的 agent_thread_id / Checkpoint
    ↓
从历史业务状态继续执行
```

规则如下：

1. 新节点的 `parent_node_id` 指向来源历史节点。
2. 新分支记录 `source_branch_id` 和 `source_node_id`。
3. 不复制旧 Checkpoint 和完整会话消息。
4. 新节点只继承来源节点冻结的 `handoff_context`。
5. 原分支、历史节点和方案版本保持不变。

## 11. 数据字段建议

`workflow_nodes` 建议包含：

```text
input_context       JSONB
result_data         JSONB
result_summary      TEXT
handoff_context     JSONB
result_version      INTEGER
agent_thread_id     VARCHAR
checkpoint_id       VARCHAR
result_updated_at   TIMESTAMPTZ
```

- `input_context`：节点启动时接收到的交接数据。
- `result_data`：Agent 最后一次保存的阶段结果。
- `handoff_context`：节点完成后交给后续节点的累计业务状态。
- `result_version`：用于乐观锁、幂等更新和防止旧页面推进新结果。
- `agent_thread_id`：当前节点 LangGraph Checkpoint 的线程标识。

如需审计每次更新，可后续增加 `workflow_node_result_versions`；MVP 可以先保留最新结果和版本号。

## 12. 并发与幂等

1. `save_stage_result` 使用 `node_id + result_version` 做乐观锁。
2. 重复保存相同结果时返回当前版本，不重复增加版本号。
3. `advance` 使用节点和结果版本作为幂等依据。
4. 一个节点只能成功创建一个默认下一节点。
5. 已完成节点禁止继续更新结果。
6. 重复点击“进入下一步”时返回已经创建的下一节点。

## 13. 系统职责

### Hai-agent

负责项目、阶段、节点、分支、阶段结果、推进校验和交接上下文。

### AI-backend

负责执行阶段 Agent、管理节点内部 Checkpoint，并提供附件、知识库、MCP 和 A2A 能力。

### Agent

负责理解当前阶段目标、与用户交互，并通过 `save_stage_result` 保存阶段结果；无权推进工作流或创建分支。

### 前端

负责展示阶段结果、根据 `can_advance` 控制按钮状态、由用户触发进入下一步，并展示历史分支。

## 14. 最终模型

> 一个步骤节点对应一次阶段 Agent 执行和一套独立 Checkpoint；Agent 使用通用工具保存 JSON 阶段结果，用户确认后由工作流服务冻结节点、构建交接上下文，并创建带有新 Checkpoint 的下一节点。

该模型不依赖跨阶段共享完整会话历史，能够降低上下文污染和 Token 消耗，并天然支持历史回溯、分支创建、阶段隔离和执行审计。
