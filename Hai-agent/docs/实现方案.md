# Hai-agent 活动策划方案智能体实现方案

## 1. 文档目标

本文用于定义 Hai-agent 的产品流程、系统边界、智能体编排、状态管理、树状分支、知识库检索、数据模型和分阶段实施计划，作为后续原型、数据库、API 与代码开发的共同基线。

## 2. 项目定位

Hai-agent 面向会展公司营销策划部门，辅助策划人员把客户提供的 Brief、品牌资料、会议纪要和补充反馈，逐步转化为可执行、可确认、可修改、可追溯的活动策划方案。

系统不是“一次输入、一次生成”的文案工具，而是一套由 Agent 驱动、业务人员持续确认的策划工作台。

### 2.1 核心目标

1. 统一整理散落在附件和对话中的项目资料。
2. 在写方案前识别需求缺失与信息冲突，减少返工。
3. 先确认策划方向和方案结构，再分阶段生成正文。
4. 每次修改都保留来源、版本和上下文。
5. 支持从任意历史节点创建新分支，比较不同方案路线。
6. 利用企业历史优秀方案与行业案例提高创意质量和落地性。

### 2.2 非目标

第一版暂不负责 CRM、合同、报价审批、项目排期、供应商管理和现场执行管理。预算只作为策划约束信息，不建设完整财务系统。

## 3. 总体架构

推荐将 Hai-agent 定位为业务编排系统，现有 AI-backend 继续作为通用 AI 能力平台。

```text
Vue + TypeScript 前端
        |
        | HTTP / SSE
        v
Hai-agent FastAPI 业务编排层
  |- 项目与资料管理
  |- 五阶段工作流
  |- 树状节点与分支
  |- 方案版本管理
  |- AI-backend 能力接入与业务工具
  |- 对外 MCP 业务工具
        |
        | Agent API / MCP
        v
AI-backend 通用能力层
  |- Agent 模板与运行
  |- 模型配置
  |- 附件解析能力
  |- 会话、流式输出和中断
  |- A2A、规划模式和通用工具
        |
        v
模型服务 / PostgreSQL / 文件存储
```

### 3.1 服务职责

| 模块 | 主要职责 |
|---|---|
| Hai-agent 前端 | 项目工作台、资料上传、确认卡片、任务树、方案编辑、版本与分支切换 |
| Hai-agent 后端 | 本地用户登录、JWT 鉴权、项目业务状态、流程约束、树状分支、方案版本、知识库绑定、业务 API 和 MCP 工具 |
| AI-backend | 通用 Agent 创建与执行、模型调用、工具装配、附件解析、SSE、中断和运行追踪 |
| PostgreSQL | 项目权威数据、业务快照、方案版本、全文索引、向量数据与 LangGraph Checkpoint |
| 文件存储 | 客户原始资料、转换后的 Markdown、最终导出文件 |

### 3.2 核心边界原则

1. 项目阶段能否流转由 Hai-agent 工作流控制，不能完全交给模型自由决定。
2. Agent 负责理解、提炼、生成和提出建议；业务服务负责校验、持久化和状态迁移。
3. PostgreSQL 中的业务快照是可回溯数据的权威来源。
4. LangGraph Checkpointer 保存运行过程和节点执行状态，不替代项目数据、方案版本和历史树。
5. Hai-agent 与 AI-backend 通过 API/MCP 交互，不跨服务直接访问对方数据库。
6. 历史节点原则上不可变；回到历史节点继续工作时创建新分支，不覆盖旧结果。
7. Hai-agent 本地维护登录用户，但第一版不建设角色、菜单和细粒度权限；项目归属从 JWT 的 `sub=user_id` 获取。

## 4. 用户完整链路

### 4.1 创建项目

用户创建活动策划项目，填写项目名称、客户名称、活动类型和预计时间等最基础信息。系统生成：

- `project_id`
- 默认主分支 `main`
- 根节点“项目已创建”
- 当前阶段 `preparation`

此时允许信息不完整，后续由 Agent 从附件和对话中补齐。

### 4.2 项目准备

1. 用户上传客户 Brief、品牌资料、历史方案、会议纪要等文件。
2. 文件服务保存原始文件并转换为 Markdown。
3. Agent 读取附件清单，按需查看正文，不把所有长文档一次性塞入上下文。
4. Brief 分析 Agent 提取项目事实，形成结构化准备清单。
5. 每项信息必须保留来源文件、原文证据和置信度。
6. 系统把提取结果保存为节点快照，并进入需求确认阶段。

准备清单建议包含：

- 活动名称与类型
- 客户与品牌
- 活动背景
- 核心目标
- 目标受众
- 时间与地点
- 预算范围
- 活动规模
- 品牌调性与视觉风格
- 必须包含的内容
- 禁止项与合规限制
- 交付物要求
- 待确认问题
- 冲突信息

### 4.3 需求确认

1. 系统先展示已确认、待确认、存在冲突三类信息。
2. Agent 只针对影响方案方向的关键缺失项发起追问，避免一次询问过多问题。
3. 前端使用结构化确认卡片，不把确认动作混成普通新对话。
4. 用户可以确认、修改、补充或标记暂不确定。
5. 每次提交都生成新的需求快照节点。
6. 达到最低完整度后，用户明确确认需求基线，流程才能进入策划思路阶段。

最低完整度建议至少具备：活动目标、受众、时间范围、预算级别、活动形式、关键限制。无法确认的信息可以标记为假设，但必须在方案中显式说明。

### 4.4 策划思路

1. Agent 根据需求基线构造知识库查询。
2. Hybrid Search 检索企业优秀方案、行业案例、创意环节和执行经验。
3. Agent 生成 2～4 个差异明确的策划方向，而不是只生成一个答案。
4. 每个方向包含核心主题、创意概念、受众体验、核心环节、适用原因、风险和参考案例。
5. 用户可选择一个方向、组合多个方向或提出修改意见。
6. 选定方向后形成策划方向基线，并生成对应树节点。

知识库结果必须作为参考证据使用，不能整段复制历史方案；生成内容应标记参考来源。

### 4.5 方案生成

方案生成采用“先大纲、后章节、再整合”的方式：

1. 根据需求基线和策划方向生成方案大纲。
2. 用户确认大纲或提出调整。
3. Agent 按章节逐步生成正文。
4. 每完成一个章节立即保存，不等待整份方案全部完成。
5. 生成过程中可继续检索案例、环节设计和执行经验。
6. 全部章节完成后执行一致性检查，重点检查目标、预算、时间、受众和活动环节是否相互矛盾。
7. 生成一个不可变的方案版本。

方案建议结构：

- 项目背景与需求理解
- 活动目标
- 核心策略
- 主题与创意概念
- 整体流程
- 重点环节设计
- 内容与传播建议
- 场地与视觉方向
- 执行重点
- 风险与应对
- 预算配置建议
- 项目排期
- 附录与参考来源

### 4.6 反馈修改

1. 用户选中整份方案、某个章节或一段内容提出反馈。
2. 系统识别修改范围和可能影响的其他章节。
3. Agent 先给出修改计划；重大修改需要用户确认。
4. 修改后生成新方案版本，并保存差异摘要。
5. 小改动留在当前分支；改变需求基线或核心创意方向的修改建议创建新分支。
6. 用户可以比较不同版本或不同分支，并将某个分支设为当前采用方案。

## 5. Agent 与工作流设计

第一版不建议把每个步骤都拆成独立 Agent。优先使用一个主编排图配合少量专业 Agent，降低上下文转移和失败恢复复杂度。

### 5.1 Agent 角色

| Agent | 职责 |
|---|---|
| Project Orchestrator | 判断当前阶段、选择下一节点、整合专业 Agent 结果 |
| Brief Analyst | 解析附件和对话，提取准备清单、缺失项和冲突项 |
| Creative Strategist | 检索案例并生成差异化策划方向 |
| Proposal Writer | 生成大纲和章节内容，维护表达一致性 |
| Proposal Reviewer | 检查需求覆盖、逻辑冲突、可执行性和引用情况 |
| Revision Agent | 根据反馈判断影响范围并生成修改版本 |

### 5.2 LangGraph 主图

```text
load_project
    -> prepare_materials
    -> analyze_brief
    -> requirement_gate
        -> interrupt: requirement_confirmation
    -> retrieve_cases
    -> generate_directions
    -> direction_gate
        -> interrupt: direction_confirmation
    -> generate_outline
    -> outline_gate
        -> interrupt: outline_confirmation
    -> generate_sections
    -> review_proposal
    -> persist_version
    -> wait_feedback
        -> revise / branch / finish
```

每个节点必须具备清晰输入、结构化输出、幂等键、状态记录和失败策略。模型不得直接修改数据库，必须通过受控服务或业务工具写入。

### 5.3 人机中断

统一中断消息：

```json
{
  "type": "requirement_confirmation",
  "data": {
    "node_id": "node_xxx",
    "title": "请确认项目需求",
    "content": {},
    "allowed_actions": ["approve", "modify", "cancel"]
  }
}
```

用户恢复消息：

```json
{
  "type": "requirement_confirmation",
  "data": {
    "action": "modify",
    "form_data": {},
    "comment": "预算暂定为 80 万"
  }
}
```

恢复时必须校验中断类型、项目、分支、节点和当前状态，防止旧卡片重复提交或跨分支恢复。


## 6. 状态模型

### 6.1 项目阶段

```text
preparation           项目准备
requirement_confirm   需求确认
creative_direction    策划思路
proposal_generation   方案生成
feedback_revision     反馈修改
completed             项目完成
cancelled             项目取消
```

阶段迁移由工作流服务控制。Agent 可以建议迁移，但必须满足业务校验条件。

### 6.2 LangGraph State

```python
class HaiProjectState(TypedDict, total=False):
    project_id: str
    branch_id: str
    current_node_id: str
    stage: str

    asset_ids: list[str]
    brief_facts: dict
    requirement_items: list[dict]
    unresolved_questions: list[dict]
    conflict_items: list[dict]
    assumptions: list[dict]

    retrieved_evidence: list[dict]
    direction_candidates: list[dict]
    selected_direction: dict | None

    proposal_outline: list[dict]
    proposal_sections: list[dict]
    current_proposal_version_id: str | None
    feedback: list[dict]

    interrupt_payload: dict | None
    last_error: dict | None
    messages: list
```

State 保存当前分支运行所需的数据，不应塞入所有历史方案正文。大型正文只保存 ID 和摘要，需要时从业务库读取。

## 7. 可回溯、可分支的树状任务流

本节的节点执行、Checkpoint 隔离和结果交接细节，以 [多阶段分支工作流与节点结果交接方案](./多阶段分支工作流与节点结果交接方案.md) 为准。

### 7.1 基本模型

```text
Project
  └─ Branch main
      ├─ Node A 项目准备
      ├─ Node B 需求确认
      ├─ Node C 策划方向 1
      └─ Node D 方案版本 1
           └─ Branch branch_2
               ├─ Node E 修改核心主题
               └─ Node F 方案版本 2
```

节点记录“某一时刻发生了什么”，分支记录“从哪个历史节点开始沿另一条路线继续”。

### 7.2 节点类型

- `project_created`
- `materials_analyzed`
- `requirements_updated`
- `requirements_confirmed`
- `directions_generated`
- `direction_selected`
- `outline_confirmed`
- `section_generated`
- `proposal_version_created`
- `feedback_submitted`
- `revision_completed`
- `branch_created`
- `error`

节点状态统一为：

- `pending`
- `running`
- `waiting_human`
- `completed`
- `failed`
- `cancelled`

### 7.3 回溯规则

1. 查看历史节点只是读取快照，不改变当前分支。
2. 从历史节点继续时，系统创建新分支。
3. 新分支的 `source_node_id` 指向选择的历史节点。
4. 系统加载该节点对应的业务快照，生成新分支初始状态。
5. 新分支首个步骤节点使用新的 LangGraph `thread_id`；后续每个步骤节点也分别创建独立 `thread_id`，避免不同阶段和分支互相污染 Checkpoint。
6. 原分支、原节点和原方案版本保持不变。
7. 用户可切换当前分支，但删除分支第一版仅允许软删除。

### 7.4 Checkpoint 与业务快照

二者必须分开：

| 数据 | 用途 |
|---|---|
| LangGraph Checkpoint | 恢复单个步骤节点内部的 Agent 运行、中断点、工具消息和执行状态 |
| Workflow Node Snapshot | 保存阶段结果和交接上下文，用于展示历史、推进节点、创建分支和审计业务状态 |
| Proposal Version | 保存可交付的完整方案内容 |
| Conversation Messages | 展示用户与 Agent 的对话 |

建议标识：

```text
conversation_id = 项目级展示会话，可按产品需要设置
thread_id       = project_id:node_id:run_id
run_id          = 一次节点执行请求
checkpoint_id   = LangGraph 自动生成
node_id         = 一个独立的步骤执行节点
```

一个步骤节点拥有独立的 `thread_id` 和 Checkpoint。节点内部发生中断或用户补充时继续使用同一 Checkpoint；节点完成后冻结业务结果并生成 `handoff_context`，下一节点创建新的 Checkpoint，只接收该交接上下文。创建分支时同样从来源节点的 `handoff_context` 恢复业务状态，不复制旧 Checkpoint 或完整消息历史。

### 8.2 约束原则

1. 同一项目内分支名称可重复，但 `branch_id` 全局唯一。
2. 工作流节点一旦完成，不允许原地修改快照。
3. 每个分支只能有一个 head node。
4. 方案版本不可覆盖，只能创建新版本。
5. 所有 Agent 保存操作必须携带 `project_id + branch_id + run_id`，支持幂等。
6. 关键 JSONB 字段进入正式开发前要定义 Pydantic Schema，不能成为无约束的大杂物箱。

## 9. 复用 AI-backend 知识库能力

Hai-agent 不再建设独立的知识库、Embedding、切片、入库任务或向量检索模块。企业历史方案和行业案例统一存入现有 AI-backend 知识库，由 AI-backend 负责：

- 知识库和文档管理
- 文件解析与切片
- Embedding 调用
- PostgreSQL 入库元数据
- Milvus 向量存储与检索
- 关键词、向量和混合检索
- Rerank
- Agent 内置知识库工具装配

### 9.1 Hai-agent 只保存知识库绑定

Hai-agent 的 `project_knowledge_bases` 只记录当前项目允许访问的外部 `knowledge_id`。这些 ID 来自 AI-backend，不建立跨服务数据库外键。

项目运行 Agent 前，Hai-agent 查询当前项目绑定的知识库，并按 AI-backend 现有接口传入：

```json
{
  "optional_features": {
    "knowledge_enabled": true
  },
  "knowledge": {
    "knowledge_base_ids": [
      "kb_company_cases",
      "kb_event_industry"
    ]
  }
}
```

知识库访问范围属于单次运行授权，不能写死在 Agent 模板中。

### 9.2 Agent 检索链路

```text
Hai-agent 读取项目绑定的 knowledge_base_ids
    -> 调用 AI-backend Agent
    -> Runtime Context 注入知识库白名单
    -> 自动挂载内置 search_knowledge_base 工具
    -> Agent 按需调用检索
    -> AI-backend 查询 PostgreSQL 元数据与 Milvus
    -> 检索结果写入 Agent State 并注入下一轮模型上下文
    -> Agent 生成策划方向或方案
    -> Hai-agent 保存实际采用的知识证据引用
```

Hai-agent 不直接连接 Milvus，也不读取 AI-backend 的知识库数据库。

### 9.3 证据追踪

AI-backend 的检索结果包含知识库、文件、切片、分数和正文。Hai-agent 只保存最终真正用于业务结果的引用快照：

- `knowledge_id`
- `file_id`
- `chunk_id`
- `source_name`
- `quote_text`
- `relevance_score`

这些字段不建立外键，因为知识库属于另一个服务；即使原文档后续下线，Hai-agent 的历史方案仍保留当时实际使用的引用文本。

## 10. Hai-agent 业务工具

Hai-agent 后端将受控业务操作暴露为 MCP 工具，AI-backend 中的 Agent 模板按需挂载。

建议工具：

| 工具 | 作用 |
|---|---|
| `get_project_context` | 获取项目、分支、阶段和当前业务快照 |
| `get_project_assets` | 获取附件清单和解析状态 |
| `read_project_asset` | 按文件和行范围读取附件 |
| `save_requirement_items` | 批量保存准备清单、证据、缺失项和冲突项 |
| `save_creative_directions` | 保存候选策划方向 |
| `save_proposal_outline` | 保存方案大纲 |
| `save_proposal_section` | 幂等保存一个方案章节 |
| `create_proposal_version` | 固化完整方案版本 |
| `save_revision_result` | 保存反馈修改结果 |

`project_id`、`branch_id`、`run_id` 等系统参数应由 Runtime Context 注入，不能依赖模型填写。模型只传业务内容。

## 12. SSE 流式事件

前端不能只监听模型文字，应按事件类型维护项目工作区。

建议事件：

- `run_start`
- `stage_changed`
- `reasoning_delta`
- `model_delta`
- `tool_call`
- `tool_result`
- `node_created`
- `node_status_changed`
- `requirement_checklist_updated`
- `interrupt`
- `direction_candidates_updated`
- `proposal_outline_updated`
- `proposal_section_delta`
- `proposal_version_created`
- `branch_created`
- `run_end`
- `error`

所有业务事件至少包含：

```json
{
  "type": "node_status_changed",
  "data": {
    "project_id": "project_xxx",
    "branch_id": "branch_xxx",
    "node_id": "node_xxx",
    "run_id": "run_xxx"
  }
}
```

前端收到清单、节点、方案等更新事件时，以服务端返回的完整对象替换本地状态，避免自行拼装造成状态漂移。

## 14. 错误恢复与一致性

### 14.1 错误分类

| 类型 | 处理 |
|---|---|
| 模型限流、网络超时 | 指数退避自动重试 |
| 工具临时失败 | 节点内有限次数重试 |
| 参数校验失败 | 把结构化错误返回 Agent，允许修正一次 |
| 附件解析失败 | 标记资料失败，允许重新解析或移除 |
| 知识检索失败 | 记录降级原因；经用户允许可不使用案例继续 |
| 持久化失败 | 当前节点失败，禁止推进阶段 |
| 用户取消 | 节点和运行标记 cancelled，保留已有结果 |

### 14.2 节点幂等

每次业务写入使用：

```text
idempotency_key = project_id + branch_id + node_id + operation
```

同一节点重试不得重复创建准备清单、策划方向和方案版本。

### 14.3 事务边界

1. 先保存业务结果，再把工作流节点标记 completed。
2. 业务保存和节点状态尽量在同一 PostgreSQL 事务中完成。
3. 外部模型和检索调用不能放在数据库事务中长期占锁。
4. 工具执行失败不能返回“成功”占位内容。
5. SSE 断开不代表任务失败，前端可通过 `run_id` 重连或查询状态。

### 14.4 可观测性

每次运行记录：

- `run_id`
- 项目、分支、节点
- Agent 模板与模型
- 开始与结束时间
- 状态和错误
- Token 与耗时
- 工具调用摘要
- LangSmith trace ID
- Checkpoint ID

LangSmith 用于模型链路分析，PostgreSQL 运行记录用于本地业务追踪，两者职责不同。

## 15. 安全与内容边界

1. 附件必须校验类型、大小和解析状态。
2. 知识库文档与用户输入都视为不可信内容，防止提示词注入。
3. 检索证据使用单独上下文标签，不能覆盖系统规则。
4. Agent 无权自行切换项目、分支或用户身份。
5. 导出方案前执行敏感信息和引用检查。
6. 所有分支、版本和删除操作保留审计记录。
7. 多租户场景下，项目、文件、知识库检索都必须带组织隔离条件。

## 17. 分阶段实施计划

### 阶段一：项目骨架与数据基线

- FastAPI、Vue、PostgreSQL Schema
- 项目 CRUD
- 资料上传与附件解析接入
- 工作流分支与节点基础表
- SSE 基础协议

完成标准：可以创建项目、上传资料、查看主分支根节点。

### 阶段二：准备与需求确认

- Brief 分析 Agent
- 准备清单
- 缺失和冲突检测
- 结构化中断确认
- 需求基线快照

完成标准：上传 Brief 后能得到带证据的项目清单，并通过卡片补齐和确认需求。

### 阶段三：知识库与策划方向

- 对接 AI-backend 知识库列表
- 配置项目知识库白名单
- 复用 Milvus Hybrid Search
- Creative Strategist
- 多方向选择卡片

完成标准：Agent 能引用企业案例生成多个策划方向，用户可选择或修改。

### 阶段四：方案生成与版本

- 大纲确认
- 分章节生成
- 方案一致性检查
- 方案版本与差异摘要
- Markdown/Word 导出

完成标准：可从确认后的方向生成完整方案，并保留每次修改版本。

### 阶段五：树状分支闭环

- 历史节点详情
- 从节点创建分支
- 步骤节点独立 Checkpoint
- 分支切换与方案比较
- 失败节点重试

完成标准：可以从任意已完成节点创建新分支，两条分支互不污染且均可继续运行。

## 18. MVP 验收标准

1. 用户能创建项目并上传至少三种常见文档。
2. Agent 能提取项目目标、受众、预算、风格、限制和证据来源。
3. 缺失或冲突信息必须进入确认环节，不能静默猜测。
4. 用户确认需求后才能进入策划方向生成。
5. 策划方向至少提供两个有明显差异的候选项。
6. Hybrid Search 返回结果包含文档与切片来源。
7. 方案必须经过大纲确认，并按章节保存。
8. 用户反馈后生成新版本，不覆盖旧版本。
9. 可从历史节点创建新分支，新旧分支状态和方案互不影响。
10. 任一节点失败后可查看原因并从该节点重试，不要求整个项目重跑。
11. 页面刷新或 SSE 断线后可通过项目、分支和运行 ID 恢复界面。
12. 所有关键业务数据均可在 PostgreSQL 中追溯。

## 19. 关键技术决策总结

1. Hai-agent 是业务编排层，AI-backend 是通用 Agent 能力层。
2. 主流程使用确定性的 LangGraph 阶段图，模型不自由控制业务状态。
3. 使用结构化中断完成需求、方向和大纲确认。
4. 使用“不可变节点 + 分支”实现回溯，不对历史状态原地覆盖。
5. 业务快照负责树状历史，Checkpointer 负责运行恢复。
6. 方案采用不可变版本，章节生成过程支持幂等续写。
7. 企业案例检索复用 AI-backend 的 PostgreSQL 元数据、Milvus 和内置知识库工具。
8. Hai-agent 通过 MCP 向 AI-backend 提供受控业务工具。
9. 系统参数通过 Runtime Context 注入，模型只负责业务内容。
10. 第一版优先保证链路正确、可恢复、可追溯，再扩展多 Agent 自动协作。
